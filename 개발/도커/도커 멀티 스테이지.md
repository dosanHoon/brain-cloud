

# 멀티 스테이지 Dockerfile 구조 정리 (base → builder → installer → runner)

규모가 큰 프로젝트를 Docker로 빌드하다 보면 이미지 용량이 불필요하게 커지거나 빌드 속도가 느려지는 경우가 많습니다. 이런 문제를 해결하기 위한 대표적인 방법이 **멀티 스테이지(Multi-stage) 빌드**입니다.

여기서는 `base → builder → installer → runner` 구조를 기준으로, `user-service`라는 가상의 Next.js 애플리케이션을 예시로 설명합니다.

---

## 1. Base 단계

```dockerfile
FROM node:20 AS base
```

- 모든 단계의 공통 기반 이미지
    
- Node.js 버전을 고정해 일관성 유지
    
- 추가 작업은 하지 않고, 이후 단계의 출발점 역할만 담당
    

---

## 2. Builder 단계

```dockerfile
FROM base AS builder
WORKDIR /app

RUN npm install -g turbo@^2.4.4

# 전체 프로젝트 복사
COPY . .

# Docker 최적화를 위해 필요 없는 패키지 제거
RUN turbo prune user-service --docker
```

- 빌드 준비 단계
    
- `turbo prune`을 사용해 다른 서비스나 불필요한 의존성을 제거
    
- 결과물로 `out/json`(최소 의존성)과 `out/full`(실제 소스)이 생성
    

이 과정을 통해 불필요한 파일 없이 빌드에 필요한 것만 추려낼 수 있다.

---

## 3. Installer 단계

```dockerfile
FROM base AS installer
WORKDIR /app

# 최소 의존성 복사
COPY --from=builder /app/out/json/ .
COPY --from=builder /app/out/pnpm-lock.yaml ./pnpm-lock.yaml

RUN corepack enable && corepack prepare pnpm@8.15.4 --activate
RUN pnpm install --frozen-lockfile

# 실제 소스 복사 및 빌드
COPY --from=builder /app/out/full/ .
RUN pnpm turbo run build --filter=user-service
```

- 최소 의존성만 설치하여 설치 속도를 개선
    
- `pnpm install` 실행 후 `user-service`를 빌드
    
- 빌드 결과로 `.next/standalone`과 `.next/static` 같은 산출물이 생성
    

---

## 4. Runner 단계

```dockerfile
FROM base AS runner
WORKDIR /app

# 보안을 위해 비root 유저 생성
RUN addgroup --system --gid 1001 nodejs
RUN adduser --system --uid 1001 appuser
USER appuser

# 빌드 산출물 복사
COPY --from=installer --chown=appuser:nodejs /app/apps/user-service/.next/standalone ./
COPY --from=installer --chown=appuser:nodejs /app/apps/user-service/.next/static ./apps/user-service/.next/static
COPY --from=installer --chown=appuser:nodejs /app/apps/user-service/public ./apps/user-service/public

CMD ["node", "apps/user-service/server.js"]
```

- installer 단계에서 생성한 빌드 산출물만 복사
    
- 불필요한 의존성이나 개발용 파일은 포함되지 않음
    
- 보안 강화를 위해 root 대신 전용 유저(`appuser`)로 실행
    

---

## 단계별 요약

|단계|역할|주요 내용|
|---|---|---|
|base|공통 기반|Node.js 버전 고정|
|builder|빌드 준비|turbo prune 실행, 최소 소스 추출|
|installer|의존성 설치 및 빌드|pnpm install, 빌드 수행|
|runner|최종 실행 환경 구성|빌드 산출물만 포함, 보안 강화|

---

## 정리

멀티 스테이지 Dockerfile 구조를 사용하면 다음과 같은 이점이 있다:

### 1) 최종 이미지 크기를 줄일 수 있다

#### 왜 줄어드는가

- 멀티 스테이지는 **마지막 `runner` 단계에 필요한 파일만** 선택적으로 `COPY --from` 하므로, 빌드 중에 생긴 대형 `node_modules`, 테스트/문서, 빌드 도구(예: turbo, pnpm) 등은 최종 이미지에 포함되지 않습니다.
    
- Next.js의 `output: 'standalone'`을 쓰면 실행에 필요한 최소 런타임 파일로 묶여 **앱 단독 실행**이 가능해집니다.
    

```js
// next.config.js (user-service)
module.exports = {
  output: 'standalone',
};
```

#### 어떻게 적용하나 (핵심 체크리스트)

- `.dockerignore`로 빌드 컨텍스트 자체를 최소화  
    예:
    
    ```
    .git
    node_modules
    **/*.log
    apps/*/.next
    ```
    
- `RUN turbo prune user-service --docker`로 **해당 앱에 필요한 것만** 추출
    
- `runner`에서 꼭 필요한 산출물만 복사
    
    ```
    COPY --from=installer /app/apps/user-service/.next/standalone ./
    COPY --from=installer /app/apps/user-service/.next/static ./apps/user-service/.next/static
    COPY --from=installer /app/apps/user-service/public ./apps/user-service/public
    ```


### 2) 빌드와 실행 환경을 분리해 관리가 용이하다

#### 왜 관리가 쉬운가

- 빌드 단계(`builder`/`installer`)는 **개발 의존성**과 빌드 도구를 자유롭게 사용하고,
    
- 실행 단계(`runner`)는 **런타임에 필요한 것만** 담으므로 역할이 명확합니다.
    
- 결과적으로 재현성(같은 소스/락파일 → 같은 산출물)이 좋아지고, 운영 이미지는 가볍고 단순해집니다.
    

#### 어떻게 적용하나 (핵심 체크리스트)

- `builder`에만 turbo/pnpm 등 빌드 도구 설치
    
- `installer`에서 설치·빌드 끝낸 뒤, `runner`로 **산출물만** 전달
    
- 환경 변수는 **빌드 타임**과 **런타임**을 분리 관리
    
    - 빌드 시 필요한 것: 공개 가능한 NEXT_PUBLIC_* 등
        
    - 런타임만 필요한 것: 서버 시크릿(예: API 키) → `docker run -e ...` 혹은 오케스트레이터의 시크릿 관리
        

### 3) 빌드 속도가 빨라져 배포 효율이 높아진다

#### 왜 빨라지는가

- 멀티 스테이지는 단계별 **레이어 캐시**를 최대 활용합니다.  
    의존성 설치 레이어가 캐시되면 이후 빌드는 소스 변경 부분만 다시 빌드합니다.
    
- `turbo prune`으로 컨텍스트·의존성 규모를 줄이면 설치/빌드가 빨라집니다.
    
- BuildKit의 캐시 마운트를 사용하면 패키지 설치 캐시를 재활용할 수 있습니다.
    

```dockerfile
# BuildKit 사용 시: pnpm 스토어 캐싱
# syntax=docker/dockerfile:1.6
RUN --mount=type=cache,target=/root/.pnpm-store \
    pnpm install --frozen-lockfile
```

#### 어떻게 적용하나 (핵심 체크리스트)

- 레이어 캐시가 잘 먹도록 `COPY` 순서 최적화
    
    - 락파일(`pnpm-lock.yaml`) → 설치 → 소스 복사 → 빌드
        
- BuildKit 활성화(`DOCKER_BUILDKIT=1`, buildx 사용) 및 캐시 마운트 도입
    
- Turborepo **remote cache**도 함께 쓰면 CI 병렬 빌드 시간을 추가로 단축 가능
