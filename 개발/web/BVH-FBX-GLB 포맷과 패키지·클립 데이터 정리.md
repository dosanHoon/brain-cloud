# BVH, FBX, GLB 포맷 차이와 패키지·클립 데이터, FBX 변환 정리

3D 모션/애니메이션을 다룰 때 자주 쓰는 **BVH**, **FBX**, **GLB** 포맷의 차이와 특징, 그리고 **패키지데이터·클립데이터**가 업계에서 어떻게 쓰이는지, **BVH/GLB를 FBX로 다운로드**하려면 어떤 변환 과정이 필요한지 정리한 문서입니다.

---

## 1. BVH vs FBX vs GLB — 포맷별 특징

### BVH (Biovision Hierarchy)

| 항목 | 내용 |
|------|------|
| **용도** | 모션 캡처 데이터 저장·분석, 바이오메카닉스·연구용 |
| **형식** | 텍스트 기반, 사람이 읽을 수 있음 |
| **내용** | 계층적 스켈레톤 + 본(joint)별 **회전 채널** (위치/오프셋 포함) |
| **좌표계** | Y-up 등 툴마다 다름. 웹(Three.js 등)에서 쓸 때는 **Z-up → Y-up** 등 축 보정이 필요할 수 있음 (예: pelvis X 90°, 그 외 본 quaternion 스왑) |
| **강점** | 단순하고 가벼움, 모션캡처 툴·리깅 툴에서 바로 내보내기 쉬움 |
| **한계** | 메쉬·머티리얼 없음. 게임/영상 파이프라인에서는 보통 **중간 포맷**으로 쓰고, FBX 등으로 한 번 더 변환해 씀 |

**정리:** 모션캡처는 BVH로 나오는 경우가 많고, 그대로 웹에서 재생하려면 BVHLoader 등으로 파싱한 뒤 스켈레톤에 매핑해야 합니다.

---

### FBX (Filmbox, Autodesk)

| 항목 | 내용 |
|------|------|
| **용도** | 3D 씬·캐릭터·애니메이션 **교환 표준** (Maya, 3ds Max, Blender, Unity, Unreal 등) |
| **형식** | 바이너리 또는 텍스트. 프로프라이터리 포맷 |
| **내용** | 메쉬, 스켈레톤, 스킨닝, **키 애니메이션**, 머티리얼, 카메라, 라이트 등 풀 씬 |
| **좌표계** | 기본이 **Z-up**인 경우가 많음. 웹(Three.js)은 Y-up이므로 로드 시 `scale 0.01`(cm→m) + 루트에 **Z-up → Y-up** 회전(`-90° X` 등)을 넣는 파이프라인이 많음 |
| **강점** | 업계 표준, 툴 간 호환성 좋음, 애니메이션·리깅 정보 풍부 |
| **한계** | 파일이 상대적으로 클 수 있음. 웹 전용으로만 쓰기엔 GLB가 더 적합할 수 있음 |

**정리:** “표준 FBX”로 내려받게 하려면, **원본이 BVH/GLB여도 최종 배포 단계에서 FBX로 한 번 변환**하는 과정이 필요합니다.

---

### GLB (glTF 2.0 Binary)

| 항목 | 내용 |
|------|------|
| **용도** | 웹, AR/VR, 모바일 등 **실시간·전송에 최적화**된 3D 포맷 |
| **형식** | glTF의 바이너리 한 덩어리 (JSON + 버퍼를 하나의 .glb로) |
| **내용** | 메쉬, 스켈레톤, 스킨닝, **키프레임 애니메이션**, 머티리얼(PBR) 등 |
| **좌표계** | glTF는 **Y-up**. 웹 엔진과 맞기 때문에, 루트에 -90° X 같은 보정을 GLB 전용 경로에서만 쓰는 경우가 있음 (특정 리그/메타리그 구조에 따라) |
| **강점** | 작은 용량, 브라우저·엔진 지원 좋음, 키 애니메이션 재생에 적합 |
| **한계** | Maya/3ds Max 등 오프라인 툴에서의 편집·교환은 FBX가 더 널리 쓰임 |

**정리:** 키 애니메이션(걷기, 뛰기, 스킬 등)은 GLB로 저장·재생하고, 사용자에게 “FBX로 다운로드”를 제공하려면 **GLB → FBX 변환**이 필요합니다.

---

## 2. 모션캡처는 BVH, 키 애니메이션은 GLB — 우리 맥락

- **모션캡처:** 실제 동작을 캡처한 데이터 → BVH로 저장·공유되는 경우가 많음.  
  웹에서는 BVHLoader2 등으로 파싱 후 pelvis 축 보정(예: X 90°), 그 외 본 quaternion 스왑 등으로 **Three.js Y-up**에 맞춥니다.
- **키 애니메이션:** DCC/엔진에서 만든 동작(Idle, Walk, Run, 스킬 등) → GLB에 넣어 웹에서 재생하기 좋음.  
  루트/메타리그에 Z-up → Y-up 보정을 넣는 경우가 있습니다.

즉, **소스 포맷**이 BVH(모션캡처) / GLB(키 애니메이션)로 나뉘어 있어도, **다운로드는 “표준 FBX” 하나로 통일**하려면 두 경로 모두 **FBX 변환 단계**를 거치는 게 좋습니다.

---

## 3. 패키지데이터·클립데이터 — 업계 표준 여부

### 클립(Clip)

- **Animation Clip**은 **게임·인터랙티브 3D 쪽에서 널리 쓰는 용어**입니다.
- Unity, Unreal 등에서 “한 덩어리의 동작” 단위를 **Clip**으로 부릅니다 (Idle, Walk, Run, Jump 등).
- glTF/Three.js에서도 `AnimationClip`이란 이름으로 동일한 개념을 씁니다.  
→ **클립(Clip)** 은 3D/애니메이션 업계에서 쓰는 **표준에 가까운 개념**입니다.

### 패키지(Package) / 패키지데이터(Package data)

- “**에셋 패키지**”는 여러 에셋(모델, 텍스처, 애니메이션 클립 등)을 **한 단위로 묶은 것**을 부르는 일반적인 표현입니다.
- Unity의 Asset Bundle, 언리얼의 패키징, 또는 “패키지 이름 + path + num_clips” 같은 **메타데이터**를 두는 방식은 프로젝트/플랫폼마다 다릅니다.
- 따라서 **“패키지데이터(packagedata)”** 라는 **이름과 스키마**(예: `name`, `path`, `num_clips`, `size`)는 **특정 서비스/DB 설계**에 따른 것이지, BVH/FBX/GLB처럼 **포맷 표준**으로 정해진 용어는 아닙니다.  
  다만 “패키지 = 에셋 묶음”이라는 **개념** 자체는 업계에서 통용됩니다.

정리하면:

- **클립:** 업계에서 널리 쓰는 **애니메이션 단위** 개념.
- **패키지데이터:** “에셋 패키지 + 메타데이터” 개념은 흔하지만, **packagedata/clipdata라는 필드 이름·구조**는 팀/시스템별 관례에 가깝습니다.

## 4. BVH·GLB를 FBX로 다운로드하기 — 표준 FBX를 거치는 변환

사용자에게 “FBX로 다운로드”를 제공하려면, **원본이 BVH이든 GLB이든** 최종적으로 **FBX 파일**을 만들어 주는 과정이 필요합니다.

### 4.1 BVH → FBX

- **목적:** 모션캡처(BVH)를 DCC/엔진에서 쓸 수 있는 **표준 FBX**로 변환.
- **방식 예:**
  - **Blender + Python:** bvh 로드 → 리깅/스케일·축 보정 → FBX 내보내기.  
    예: [bvh2fbx](https://github.com/mcsantiago/bvh2fbx) 같은 스크립트로 배치 변환 가능.
  - **온라인/데스크톱 툴:** Convert3D 등 BVH→FBX 변환기 사용.
- **주의:** BVH는 **스켈레톤+모션만** 있으므로, FBX로 내보낼 때는 “캐릭터 메쉬가 붙은 FBX”가 필요하면 **별도 메쉬 FBX와 합치거나**, 리그에 메쉬를 붙여서 내보내는 파이프라인이 필요할 수 있습니다.

### 4.2 GLB → FBX

- **목적:** 웹용 키 애니메이션(GLB)을 Maya/Unity 등에서 쓸 수 있는 **표준 FBX**로 변환.
- **방식 예:**
  - **온라인:** Aspose.3D, Convert3D 등 GLB→FBX 변환 서비스.
  - **스크립트/로컬:** Blender에서 glTF/GLB 임포트 후 FBX 내보내기, 또는 [FBX2glTF](https://github.com/facebookincubator/FBX2glTF) 계열은 주로 FBX→glTF 방향이지만, 역방향은 Blender/기타 DCC로 처리하는 경우가 많음.
- **주의:** GLB는 Y-up, FBX는 보통 Z-up이므로 내보낼 때 **축/스케일 설정**을 맞추는 것이 좋습니다.

### 4.3 “표준 FBX”로 통일할 때

- **스케일:** cm → m 등 단위를 팀 규약에 맞춤 (예: `0.01`).
- **축:** Z-up ↔ Y-up 변환을 변환 단계에서 한 번만 하면, 다운로드받은 FBX를 여러 툴에서 동일하게 쓸 수 있습니다.
- **트랙 이름:** position 트랙 등에 `item`+`position` 같은 규칙을 쓰는 경우, 변환 후에도 동일 규칙을 유지하면 기존 파이프라인과 호환하기 좋습니다.

## 5. 요약 표

| 포맷 | 주 용도 | 메쉬 | 스켈레톤/애니메이션 | 웹 재생 | 다운로드용 “표준” |
|------|--------|------|----------------------|---------|--------------------|
| **BVH** | 모션캡처, 연구 | ✗ | ✓ (계층+회전) | Loader로 가능 | → FBX 변환 필요 |
| **FBX** | DCC·엔진 교환 | ✓ | ✓ | Loader로 가능 (축/스케일 보정) | ✓ 그대로 사용 |
| **GLB** | 웹·AR/VR 키 애니 | ✓ | ✓ | ✓ 적합 | → FBX 변환 필요 |

- **클립:** 애니메이션 한 편 단위 — 업계에서 널리 쓰는 개념.
- **패키지데이터:** 에셋 묶음 + 메타데이터 개념은 흔함. “packagedata/clipdata” 스키마는 프로젝트/시스템 관례.
- **BVH·GLB를 FBX로 다운로드:** Blender/온라인 변환기 등으로 **표준 FBX를 거치는 변환 파이프라인**을 두면, 모션캡처(BVH)와 키 애니메이션(GLB)을 모두 하나의 FBX 다운로드 경험으로 제공할 수 있습니다.
