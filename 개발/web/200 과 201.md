
# HTTP 응답코드 200 vs 201

_— “성공”에도 품격이 있다! REST API 표준 뽀개기_

개발하다 보면 한 번쯤은 헷갈립니다.  
**“이거 200으로 보내? 201로 보내?”**

‘다 잘됐으면 됐지 뭐~’라고 생각했다면,  
이 포스팅을 끝까지 봐주세요.  
**성공에도 표준이 있고, 그 디테일이 API의 품질을 좌우합니다!**

---

## 1. 200 OK — “네, 정상적으로 처리됐습니다.”

- **의미:**  
    요청이 정상적으로 처리됨.  
    (가장 무난한 성공 코드)
    
- **언제 쓰나:**
    
    - 데이터 **조회**(GET)
        
    - 데이터 **수정**(PUT, PATCH)
        
    - 데이터 **삭제**(DELETE)
        
    - 기타 별다른 의미 없이 ‘잘됐다’고 말할 때
        

```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "id": 1, "name": "hoony" }
```

---

## 2. 201 Created — “방금 새로 만들었습니다!”

- **의미:**  
    새로운 리소스를 성공적으로 **생성**했을 때 사용.
    
- **언제 쓰나:**
    
    - **POST** 요청으로 회원가입, 게시글 등록 등  
        **“방금 뭔가 새로 만들어졌을 때”**
        
- **팁:**  
    Location 헤더로 새로 생성된 리소스의 주소를 알려주는 게 표준!
    

```http
HTTP/1.1 201 Created
Location: /users/123
Content-Type: application/json

{ "id": 123, "name": "newbie" }
```

---

## 3. RESTful API 표준에서의 역할

|상황|응답코드|설명|
|---|---|---|
|리소스 생성 (POST)|201|생성 완료, Location 헤더로 위치 알려줌|
|리소스 조회 (GET)|200|데이터 정상 반환|
|리소스 수정 (PUT/PATCH)|200|데이터 정상 수정, 내용 반환 가능|
|리소스 삭제 (DELETE)|200|삭제 정상 처리, 204(No Content)도 가능|
|그 외 일반 처리|200|기타 정상 응답|

---

## 4. 공식 표준 근거

- [RFC 7231, 6.3.2. 201 Created](https://datatracker.ietf.org/doc/html/rfc7231#section-6.3.2)
    
    > 서버는 201 응답 시, 가능하면 Location 헤더로 새로 만든 리소스의 URI를 제공해야 한다.
    

---

## 5. 실무에서의 팁

- **POST로 새로 만드는 API**라면 → **201 Created**  
    (Location 헤더도 가능하면 챙겨주세요!)
    
- **조회/수정/삭제/일반 처리**라면 → **200 OK**
    
- **아무 내용도 안 보내는 삭제라면** → **204 No Content**도 OK!
    

### Express 예시

```js
// Node.js(Express)
app.post('/users', (req, res) => {
  // ...생성 로직
  res.status(201).location(`/users/${newUser.id}`).json(newUser);
});
```

## 6. 결론 — 성공의 디테일이 API의 품질!

응답코드는 단순한 숫자가 아니라,  
**서버와 클라이언트가 소통하는 언어**입니다.

- “조회·수정·삭제는 200”
    
- “생성은 201, 그리고 Location 헤더까지!”
