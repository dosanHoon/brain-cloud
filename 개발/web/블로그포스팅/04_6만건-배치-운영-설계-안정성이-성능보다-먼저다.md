# 6만 건 배치 운영 설계 — 안정성이 성능보다 먼저다

> **대상 독자:** 대량 데이터 처리 배치를 처음 설계해보는 프론트엔드·풀스택 개발자
> **핵심 주제:** 중단 복구, 실패 관리, 병렬화 설계

---

## "코드 완성 = 배치 완성"이 아니었다

3D 에셋 캡처 파이프라인 코드가 동작하기 시작했을 때, 처음 든 생각은 이거였다.

> "100개 테스트는 잘 됐으니까 60,000개 그냥 돌리면 되겠네."

그렇게 돌렸더니 6시간 후에 배치가 죽어있었다.
로그도 없고, 어디서 멈췄는지도 모르고, 처음부터 다시 돌려야 했다.

이 글은 그 경험 이후에 만든 **운영 설계 원칙**을 정리한 것이다.

---

## 원칙 1: 중단 복구를 먼저 설계한다

배치가 실패할 것을 전제로 설계해야 한다.
"실패하지 않게 만든다"와 "실패해도 이어서 실행된다"는 전혀 다른 문제다.

### skip-existing 패턴

출력 파일이 이미 있으면 건너뛴다.
이 옵션 하나가 배치를 재시작 가능하게 만든다.

```javascript
// 두 파일이 모두 존재해야 완료로 인정
function isAlreadyProcessed(item) {
  return (
    SKIP_EXISTING &&
    fs.existsSync(item.webpPath) &&
    fs.existsSync(item.webmPath)
  )
}

for (const item of assetQueue) {
  if (isAlreadyProcessed(item)) {
    log(`[skip] ${item.name}`)
    stats.skip++
    continue
  }
  await process(item)
}
```

**중요:** partial output(WebM만 있고 WebP 없는 경우, 또는 반대)은 완료가 아니다.
둘 다 있어야 완료로 인정해야 재처리가 안전하다.

### 실패 로그 JSON 저장

```javascript
const failLog = []

try {
  await captureAndEncode(page, item)
  stats.ok++
} catch (err) {
  stats.fail++
  failLog.push({ path: item.path, error: err.message, time: new Date().toISOString() })
  log(`[fail] ${item.name} — ${err.message}`)
}

// 배치 종료 후 실패 목록 저장
await fs.promises.writeFile(
  'logs/fail-log.json',
  JSON.stringify(failLog, null, 2)
)
```

다음 실행에서 실패 목록만 재처리:

```javascript
// fail-only 모드
const failPaths = JSON.parse(fs.readFileSync('logs/fail-log.json'))
  .map(item => item.path)

const assetQueue = allAssets.filter(a => failPaths.includes(a.path))
```

## 원칙 2: 파일럿 없이 본 배치로 가지 않는다

6만 개 배치를 돌리기 전에 반드시 **100개 파일럿**을 먼저 돌린다.

파일럿에서 확인할 것:

| 항목 | 확인 방법 |
|------|-----------|
| 처리 속도 | 100개 시간 → 전체 예상 시간 계산 |
| 메모리 안정성 | htop/Activity Monitor로 메모리 추이 확인 |
| 실패율 | 실패 로그 확인, 재현 가능한 실패 패턴 파악 |
| 출력 품질 | 랜덤 10개 샘플 육안 확인 |
| 디스크 사용량 | 100개 출력 크기 → 전체 예상 크기 계산 |

파일럿 수치:
```
100개 처리: 9분 5초
→ 에셋당 평균: 5.45초
→ 6만 개 단순 환산: 90.8시간 (3.8일)
→ 운영 오버헤드 포함: 4~5일
→ stride 4 (워커 4개): 약 1일
```

이 수치 없이 본 배치에 들어가는 건 무계획이다.

## 원칙 3: stride 병렬화로 균등 분배

단순히 "앞에서 N개씩 잘라서" 워커에 주면 안 된다.

```
전체 100개 에셋, 워커 4개로 분배:

잘못된 방법 (순서 분할):
  Worker 0: 에셋 0~24   ← 큰 파일들이 몰릴 수 있음
  Worker 1: 에셋 25~49
  Worker 2: 에셋 50~74
  Worker 3: 에셋 75~99

올바른 방법 (stride 분산):
  Worker 0 (slot=0): 에셋 0, 4, 8, 12, ... (index % 4 === 0)
  Worker 1 (slot=1): 에셋 1, 5, 9, 13, ... (index % 4 === 1)
  Worker 2 (slot=2): 에셋 2, 6, 10, 14, ... (index % 4 === 2)
  Worker 3 (slot=3): 에셋 3, 7, 11, 15, ... (index % 4 === 3)
```

파일 목록이 보통 알파벳/번호순으로 정렬되어 있으면,
같은 폴더의 파일(크기 비슷)이 고르게 퍼진다.

```javascript
// start-batch.js — 워커 spawn
function spawnWorkers(stride, offset, limit) {
  const jobs = []
  for (let slot = 0; slot < stride; slot++) {
    const proc = spawn('node', ['scripts/batch-convert.js'], {
      env: {
        ...process.env,
        BATCH_STRIDE: String(stride),
        BATCH_SLOT: String(slot),
        BATCH_OFFSET: String(offset),
        BATCH_LIMIT: String(limit),
        APP_URL: 'http://127.0.0.1:5173',
      },
      stdio: ['ignore', outStream, errStream],
      detached: true,
    })
    jobs.push({ slot, processId: proc.pid })
    proc.unref()  // 부모 프로세스 종료 시 워커는 계속 실행
  }
  return jobs
}
```

## 원칙 4: 장시간 배치 운영 준비

3~4일짜리 배치는 일반 터미널 세션에서 돌리면 안 된다.

### tmux / screen 사용

```bash
# tmux 세션 시작
tmux new -s batch

# 배치 실행
pnpm run batch:start -- --stride 4 --limit 60000

# 세션 분리 (Ctrl+B, D)
# → SSH 끊어도 배치는 계속 실행

# 나중에 다시 접속
tmux attach -t batch
```

### 로그 분리 저장

```javascript
// 워커별 로그 파일 분리
const outLog = `logs/batch-slot${slot}.out.log`
const errLog = `logs/batch-slot${slot}.err.log`
```

로그 실시간 확인:
```bash
tail -f logs/batch-slot0.out.log
```

## 원칙 5: 구간 재실행으로 유연한 복구

전체를 처음부터 다시 돌리지 않아도 된다.

```bash
# 에셋 500~599번만 다시 처리
pnpm run batch:start -- --stride 4 --offset 500 --limit 100

# 에셋 0번부터 200번까지만 처리
pnpm run batch:start -- --stride 2 --offset 0 --limit 200
```

`SKIP_EXISTING`이 활성화되어 있으면, 이미 완료된 에셋은 자동으로 건너뛴다.
처음부터 다시 돌려도 완료된 것은 건드리지 않는다.

## 실제 운영 흐름

```
1. S3에서 에셋 다운로드
   pnpm run download:clips

2. 파일럿: 100개 먼저 처리
   pnpm run batch:start -- --stride 2 --limit 100

3. 품질/성능 확인 후 본 배치 시작
   tmux new -s batch
   pnpm run batch:start -- --stride 4 --limit 60000

4. 진행 상황 모니터링
   tail -f logs/batch-slot0.out.log

5. 완료 후 S3 업로드
   pnpm run upload:clips

6. 실패 목록 재처리 (필요 시)
   # fail-log.json에서 실패 목록 확인 후 재실행
```

## 결론: 배치 안정성 체크리스트

- [ ] `SKIP_EXISTING` 옵션 있음 (중단 후 재개 가능)
- [ ] partial output 감지 및 삭제 로직 있음
- [ ] 실패 로그 JSON으로 저장
- [ ] 100개 파일럿 먼저 돌려 속도/품질 확인
- [ ] stride 분배로 워커 간 균등 분배
- [ ] tmux/nohup으로 장시간 세션 유지
- [ ] 워커별 로그 파일 분리
- [ ] 구간 재실행(`--offset`, `--limit`) 지원

**코드가 완성된 뒤 이 체크리스트를 통과해야 배치가 완성된 것이다.**
