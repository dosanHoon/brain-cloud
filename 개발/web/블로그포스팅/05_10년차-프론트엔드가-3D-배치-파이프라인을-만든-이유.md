# 10년차 프론트엔드가 3D 배치 파이프라인을 만든 이유

> **대상 독자:** 프론트엔드 경력이 쌓이면서 "나는 어떤 엔지니어가 되고 싶은가"를 고민하는 개발자
> **핵심 주제:** 프론트엔드의 역할 확장, 파이프라인 오너십, 커리어 포지셔닝

---

## 프론트엔드 10년, 그런데 뭘 잘하는 사람인가?

경력이 쌓이면 이상한 질문이 생긴다.

> "나는 리액트 컴포넌트 잘 만드는 사람인가, 아니면 문제를 해결하는 사람인가?"

UI 컴포넌트를 잘 만드는 것은 중요하다. 하지만 10년 경력에 "저 리액트 잘 써요"는 포지셔닝이 약하다.
시니어 프론트엔드에게 기대하는 것은 **"문제를 정의하고, 전체를 설계하고, 끝까지 책임지는 능력"** 이다.

이 3D 배치 파이프라인 프로젝트는 그 관점에서 내가 어떤 엔지니어인지를 보여주는 작업이었다.

---

## 이 프로젝트가 보여주는 것

### 1. 기술 선택의 근거를 가진다

처음에 "Python + Blender headless"를 고려했다.
그런데 이미 동작하는 Three.js 뷰어가 있었고, 거기엔 GLB/FBX/BVH 로더, 리타게팅 로직, 애니메이션 믹서가 전부 포함되어 있었다.

새로운 스택을 처음부터 만드는 것보다 **기존 코드를 뒤집어서 자동화 파이프라인에 집어넣는 것**이 훨씬 현실적이었다.

이 판단이 "경험"이다. 경험이 없으면 새 스택을 만드는 쪽을 선택한다.

### 2. 브라우저와 서버의 경계를 허문다

```
Three.js (브라우저) + Puppeteer (Node.js) + FFmpeg (시스템)
```

이 세 개를 연결하는 것은 프론트엔드 스킬만으로도, 백엔드 스킬만으로도 안 된다.
브라우저 렌더링 원리를 알고, Node.js child_process를 다루고, FFmpeg 인코딩 옵션을 이해해야 한다.

프론트엔드 엔지니어가 이 스택 전체를 설계하고 구현했다는 것이 포인트다.

### 3. 운영 관점을 가진다

코드가 100개에서 동작하는 것과 6만 개에서 안정적으로 동작하는 것은 다른 문제다.

- `SKIP_EXISTING`: 배치가 죽어도 처음부터 다시 시작하지 않는다
- stride 병렬화: 워커 간 처리 시간이 균등하다
- 페이지 재시작: 메모리 누수가 없다
- 실패 로그 JSON: 실패한 것만 재처리한다

이 결정들은 코드 기술이 아니라 **운영 경험**에서 나온다.

### 4. 숫자로 말한다

```
100개 실측: 9분 5초 = 5.45초/에셋
6만 건 환산: 90.8시간 (3.8일)
stride 4 적용: 약 1일
```

막연한 "오래 걸릴 것 같아요"가 아니라 수치로 의사결정을 한다.
이게 10년차와 3년차의 차이다.

---

## 프론트엔드의 영역은 어디까지인가

나는 이 프로젝트에서 이런 걸 했다.

| 영역 | 내용 |
|------|------|
| **WebGL/Three.js** | 씬 설정, 카메라, 애니메이션 믹서, 리타게팅 |
| **브라우저 API** | canvas.toDataURL, window 전역 API 설계 |
| **Node.js 자동화** | Puppeteer 제어, child_process, 파일 시스템 |
| **FFmpeg** | VP9 인코딩, stdin 스트리밍, 코덱 옵션 |
| **AWS S3** | 대용량 다운로드/업로드, 재시도 로직 |
| **운영 설계** | 배치 병렬화, 실패 복구, 로그 관리 |
| **성능 분석** | 병목 측정, 파라미터 튜닝, 벤치마크 |

이걸 "프론트엔드 영역"이라고 부르기에는 너무 넓다.
하지만 **시작점이 브라우저 앱**이었고, **모든 설계 결정의 기반이 웹 기술**이었다.

프론트엔드의 영역은 "UI를 만드는 것"이 아니라 "웹 기술로 해결할 수 있는 모든 것"이다.
그리고 웹 기술로 해결할 수 있는 것의 범위는 생각보다 훨씬 넓다.

## 이런 경험을 어떻게 어필하나

이력서나 포트폴리오에서 이 프로젝트를 설명할 때 중요한 것:

**틀린 방법:**
> "Three.js, Puppeteer, FFmpeg, AWS S3 사용 경험"

**맞는 방법:**
> "브라우저 기반 3D 뷰어를 Puppeteer로 제어하는 배치 자동화 파이프라인 설계 및 구현. 6만 건 에셋 처리를 위한 stride 병렬화와 중단 복구 아키텍처 적용. 100개 파일럿 기준 5.45초/에셋, stride 4 적용 시 1일 내 완료 달성."

기술 나열이 아니라 **문제 → 설계 → 결과**로 말한다.

---

## 마치며

10년차 프론트엔드 엔지니어의 가치는 많은 기술을 아는 것에서 오지 않는다.

- 문제를 정의하고
- 현실적인 해결책을 선택하고
- 전체를 설계하고
- 운영까지 생각하고
- 수치로 증명하는 것

이 프로젝트는 그 모든 것을 포함하고 있었다.
그래서 "잘 됐다"가 아니라 "내가 어떤 엔지니어인지 보여주는 작업"이 됐다.
