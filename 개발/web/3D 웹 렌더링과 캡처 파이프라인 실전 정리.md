
## 배경
`three.js + React + Puppeteer + ffmpeg`로 3D 모션 에셋(BVH/FBX/GLB)을 웹에서 렌더링하고, 정적 썸네일(WebP)과 동영상(WebM)을 배치로 만드는 과정에서 확인한 실전 포인트를 정리한다.

## 1) 브라우저에서 보이는 화면과 캡처 결과가 다를 수 있다
같은 `CaptureApp`라도 다음 조건이 바뀌면 캡처 결과가 달라진다.

- GPU 렌더링 vs CPU 소프트웨어 렌더링(SwiftShader)
- 인코딩 단계(특히 VP9 압축)
- 픽셀 포맷(`yuv420p` vs `yuv444p`)

핵심은 "렌더링 결과"와 "최종 인코딩 결과"를 분리해서 봐야 원인을 빨리 찾을 수 있다는 점이다.

## 2) CPU-only 환경에서는 배경 디테일이 쉽게 죽는다
GPU 없는 서버에서는 WebGL이 소프트웨어 렌더러로 돌아가며, 그리드 같은 얇은 디테일이 약해질 수 있다.

- 서버에서 캡처는 가능하다.
- 하지만 품질과 속도는 GPU 환경보다 크게 불리하다.
- 특히 바닥 그리드/미세 텍스처는 체감 품질 저하가 먼저 보인다.

**( CPU-only 서버 비추 )**

## 3) 카메라 안정화는 고정 시간이 아니라 "프레임 수"로 관리 중
현재 파이프라인은 "카메라 안정화 감지" 로직이 아니라, 웜업 프레임을 버리는 방식이다.

- `CAPTURE_WARMUP_FRAMES=15`처럼 고정 프레임 버림
- 의미: 캡처 시작 전에 재생을 먼저 진행해 초기 흔들림 구간 제외
- 장점: 구현 단순, 예측 가능
- 단점: 에셋별 최적값이 다름

## 4) CaptureApp 기준으로는 "카메라 로딩 완료 시간" 고정값이 없다
코드상 `captureReady`는 에셋 로드 완료 시점에 true로 올라간다. 이후 카메라 팔로우 보간(`lerp`)과 컨트롤 damping으로 자연스럽게 수렴한다.

즉 "항상 몇 초 후 안정화" 같은 단일 숫자는 없고, 에셋 모션 특성에 따라 달라진다.

## 5) 해상도/그리드/배경 튜닝은 품질-속도 교환 문제
작업 중 실제로 다음 이슈가 반복됐다.

- 해상도를 올리면 품질은 좋아지지만 처리 시간이 급증
- 그리드를 두껍게 하면 CPU-only에서도 보이기 쉬우나 화면 인상이 달라짐
- 배경 톤/안개(Fog)/조명 세팅이 조금만 바뀌어도 전체가 어둡거나 평평해 보일 수 있음

결론적으로 "기본 미감"을 먼저 고정하고, 성능 튜닝은 인코딩/병렬에서 먼저 하는 편이 안정적이다.

## 정리
"웹에서 잘 보인다"와 "배치 결과가 좋다"는 별개다. 3D 배치 파이프라인은 아래 3단계를 분리해 점검해야 한다.

1. 렌더링(카메라/조명/배경/그리드)
2. 캡처 타이밍(웜업, 시작 프레임)
3. 인코딩(코덱/픽셀포맷/품질)

이 셋을 나눠서 보면 원인 추적 속도가 크게 빨라진다.
