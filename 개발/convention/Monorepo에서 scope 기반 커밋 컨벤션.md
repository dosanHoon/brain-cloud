# Monorepo에서 Scope 기반 커밋 컨벤션 — 팀이 함께 쓰는 실전 룰

> "feat이랑 fix는 쓰는데, scope는 뭘로 넣지?"  
> Turborepo·Nx 같은 모노레포에서 **어디를 건드렸는지** 한눈에 보이게 하는 방법을 정리해봤어요.

`feat`, `fix` 같은 **타입**은 이제 많은 팀이 쓰지만, **scope**를 어떻게 정할지까지 정한 팀은 생각보다 적어요.  
모노레포에서는 앱/패키지가 여러 개라서, scope를 **파일 경로 기준**으로 고정해두면 이력 읽기·자동화·리드님이 바뀐 범위 파악하기가 훨씬 수월해집니다.

이 포스팅에서는 **scope를 “어디를 수정했는지”에 묶는 실전 컨벤션**을 소개해요.

---

## 1. 왜 Scope를 정할까?

- **이력만 봐도 변경 범위를 알 수 있음**  
  `feat(admin): 대시보드 필터 추가` → admin 앱만 건드렸구나.
- **CI/배포/릴리즈 노트 자동화**  
  scope별로 “이번 배포에 admin만 포함” 같은 걸 스크립트로 짤 수 있음.
- **코드 리뷰·담당 영역 파악**  
  “이번 스프린트에 web 쪽 변경이 많네” 같은 인사이트를 커밋 로그만으로 얻을 수 있음.

---

## 2. Scope = “변경된 파일 경로”로 고정하기

scope를 **팀원마다 다르게 해석하지 않도록**, **디렉터리 구조에 맞춰 고정**하는 걸 추천해요.

### 예시: 앱·패키지 구조

```
apps/
  web/             ← 사용자용 웹 앱
  admin/           ← 관리자용 앱
packages/
  ui/              ← 공용 UI 컴포넌트
  utils/           ← 공용 유틸
  types/           ← 공용 타입
```

### scope 매핑 (파일 경로 기준)

| scope   | 적용 경로 예시              | 의미           |
|--------|-----------------------------|----------------|
| `web`  | `apps/web/**`              | 사용자용 웹 앱   |
| `admin`| `apps/admin/**`            | 관리자 앱       |
| `ui`   | `packages/ui/**`           | 공용 UI 패키지  |
| `common`| 그 외 `packages/*`, 루트 설정 | 공용 패키지·설정 |

**규칙 한 줄:**  
“이번 커밋에서 수정한 파일 중 **가장 의미 있는 하나**의 경로를 골라, 그에 해당하는 scope를 쓴다.”

여러 scope에 걸치면, **가장 비중 큰 쪽 하나**만 쓰거나, 팀 룰에 따라 `common`으로 통일해도 됩니다.

---

## 3. 커밋 메시지 형식

```
<type>(<scope>): <subject>
```

- **type**  
  기존처럼 `feat`, `fix`, `docs`, `refactor`, `chore`, `build`, `ci` 등.
- **scope**  
  위 표의 `web` | `admin` | `ui` | `common` (팀 구조에 맞게 정의).
- **subject**  
  한 줄 요약. 가능하면 한국어로, 명령형으로 (예: “추가”, “수정”, “구현”).

### 예시

```
feat(web): 로그인 페이지 UI 구현
fix(admin): 대시보드 데이터 로딩 에러 수정
refactor(ui): 버튼 컴포넌트 스타일 개선
chore(common): turbo.json 설정 변경
build(common): 루트 package.json 스크립트 정리
```

---

## 4. 실무에서 쓰는 팁

- **루트 설정만 바꾼 경우**  
  `turbo.json`, 루트 `package.json`, 공통 ESLint 등 → `common`.
- **여러 앱/패키지를 동시에 수정**  
  “가장 영향 큰 곳” 하나만 scope로 쓰거나, 팀 합의로 `common` 고정.
- **문서만 수정**  
  `docs(common): …` 또는 해당 앱이 있으면 `docs(web): …` 등으로 일관되게.
- **자동화하고 싶다면**  
  lint 스테이지에서 “변경 파일 목록 → scope 후보”를 추천해주는 스크립트나 Cursor/IDE 룰을 두면 더 일관되게 유지할 수 있어요.

---

## 5. 정리

- **타입**은 “무슨 종류의 변경인지”, **scope**는 “어디를 바꿨는지”를 나타내게 두자.
- scope를 **파일/디렉터리 기준**으로 고정하면, 팀 전체가 같은 규칙으로 쓸 수 있고, 나중에 자동화·분석에도 유리하다.
- 모노레포에서는 “앱·패키지 단위 = scope”로 매핑해두는 것이 가장 단순하고 확장하기 좋다.

작은 룰 하나가 팀의 커밋 이력과 협업 품질을 크게 바꿔줍니다.  
이미 타입만 쓰고 있다면, 이번에는 **scope까지** 한 번 정해보는 걸 추천해요.
